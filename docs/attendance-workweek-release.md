# إصدار إعداد أيام العمل والراحة

## ما ينتقل بالنشر
تُنشر إضافة ثلاثة جداول للتقويم والسياسات والمراجعات، مع الشاشات والمنطق المرتبط بها. لا توجد تعبئة تلقائية لبيانات الإنتاج أو حذف جداول، ولا يُنقل إعداد التجربة أو موظفو الاختبار من التطوير إلى الإنتاج.

ينبغي أن تعرض معاينة Publish إضافات الجداول التالية فقط لهذا التغيير:
- `attendance_week_policies`
- `attendance_day_calendars`
- `attendance_calendar_reviews`

إذا عرضت المعاينة حذف جدول أو عمود أو بيانات، توقف وراجع الفرق قبل الموافقة. لا تستخدم `db:push` العام لمعالجة الاختلافات؛ توجد جداول تشغيل قديمة يجب الحفاظ عليها.

## اعتماد إعداد الإنتاج
1. بعد النشر افتح مساحة الموارد البشرية ثم **إعدادات الدوام**.
2. اختر **أيام العمل** ثم **القاعدة العامة**.
3. الإعداد المقترح: السبت إلى الخميس للعمل، والجمعة للراحة. اختر تاريخ السريان بدءًا من الغد.
4. اترك تخصيصات الموظفين محفوظة افتراضيًا. إدراجها في القاعدة العامة يحتاج اختيارًا صريحًا. التخصيصات المؤجلة لما بعد تاريخ السريان تبقى ظاهرة في سجل السياسات.
5. اكتب السبب، وافتح **معاينة**، وراجع العدد والأيام قبل وبعد والاستثناءات، ثم أكد الاعتماد.
6. لتخصيص موظف أو مجموعة اختر الموظفين بالأسماء/الأرقام، أو أعدهم إلى القاعدة العامة من نفس النموذج.

## مراجعة السبت الجاري أو السابق
اختيار أسبوع جديد لا يعيد كتابة تاريخ الموظفين. افتح **مراجعة يوم**، واختر التاريخ والموظفين المطلوبين صراحة، ثم حدد يوم عمل أو راحة والسبب. تعرض المعاينة الحالة المتوقعة قبل الاعتماد؛ قد تظهر حالة تقصير إذا كانت أدلة اليوم مكتملة.

البصمات الأصلية لا تتغير. عند غياب جدول يومي محفوظ مكتمل أو وقت نهاية موثق، يبقى التقييم غير متاح ولا ينشأ غياب أو تأخير تلقائي. تعرض شاشة الحضور تحذيرًا للأيام ذات سياسة الأسبوع غير المعتمدة، ولا تدخل في نقاط المخاطر.

يمكن مراجعة موقع البصمة والورديات وتعيين الموظفين من الروابط أعلى صفحة الإعدادات. هذه الإعدادات مستقلة عن أيام العمل ولا تُستبدل بتغيير الأسبوع.

## فحوص التطوير
اختبارات PostgreSQL تنشئ موظفين ومديرًا اصطناعيين، ولا ترسل رسائل SMS، وتزيل بياناتها بعد الاختبار. يمكن تشغيل `npm test`. فحص TypeScript العام يضم أخطاء سابقة خارج نطاق الحضور؛ بناء الإصدار مستقل عنه.
